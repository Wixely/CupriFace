# CupriFace Roadmap

The core milestones **M0–M9 are complete** (engine, layout, text, paint, binding, components,
interaction, Windows a11y (UIA), AOT trim-clean, WASM host) — see [DESIGN.md §12](DESIGN.md).
This document tracks everything **considered but not yet implemented**: the deferred refinements
called out in the design plus items we've since scoped. Rows that have since shipped stay, marked
🟢 with what proves them — a roadmap that quietly deletes its own history stops being checkable.
It is a living list, not a commitment of dates.

**Status legend:** 🔴 not started · 🟡 partial / scaffolded · 🟢 prototyped, needs hardening
**Priority:** **P1** (core to the product's promises) · **P2** (important) · **P3** (nice to have)

---

## 1. Accessibility bridges (P1)

The platform-neutral **semantics tree** is real (identity, focus, states, on-screen bounds), and
**four platforms now have working bridges** — UIA (Windows), AT-SPI (Linux), NSAccessibility
(macOS) and TalkBack (Android, §11) — each with a blocking CI gate driven by a real
assistive-technology client, plus the web's hidden-DOM mirror. What remains is refinement inside
each, and a human screen-reader pass.

| Item | Status | Notes |
|------|--------|-------|
| Complete **UIA** provider (Windows) | 🟢 | **Done (2026-08), proven by a blocking CI gate.** The window answers `WM_GETOBJECT` with a UIA fragment tree built from the semantics tree — on BOTH Windows paths (the GL window and the SDL software window, which is what GPU-less machines — RDP, VMs, the CI runner — actually run). Patterns per role: Invoke (button/link/menuitem), Toggle (checkbox/switch), SelectionItem (radio/tab/option/treeitem), RangeValue (slider read+write, progressbar/spinbutton read), Value (textbox/combobox, read for now), ExpandCollapse (`aria-expanded`), Selection (containers). Threading: UIA calls read an immutable snapshot published after each drawn frame; actions queue to the UI thread and run through the same machinery as a real click (`AccessibilityActivate`/`Focus`/`SetValue`, path-addressed so handles survive the per-keystroke rebuild); focus changes raise UIA focus events (what makes Tab talk). Names include positional labels — the same sibling association clicks use, so Narrator's announcement and the click target can't disagree. The gate (`tests/UiaSmoke`, FlaUI — a real UIA client): tree served, a named checkbox toggles, a slider answers a RangeValue write, Tab focus visible. Interop is one file mirroring UIAutomationCore.idl (the WindowsDesktop managed wrapper would ~4× a self-contained publish); `CUPRIFACE_UIA=0` is the kill switch. Remaining inside this item: Text pattern for editable fields, Value.SetValue, UIA events beyond focus (property/structure changed). One caveat stated plainly: the gate exercises the SDL path (the runner is GPU-less, like every RDP/VM box) — the GL window carries identical wiring but no CI machine can run GL-on-Windows to prove that combination, **and a 2026-08-21 observation sharpens this from "unproven" to "suspect"**: during the keyboard-zoom hunt, a Tab delivered to the GL window (its own key log records the keydown) produced no UIA-visible focus change, while the same press on the SDL window moves focus. Follow-up: GL-window UIA focus. |
| **AT-SPI** bridge (Linux) | 🟢 | **Done (2026-08), proven by a blocking CI gate.** The app joins the accessibility bus as an AT-SPI application (`org.a11y.Bus.GetAddress` → connect → `Socket.Embed` with the registry) and serves the semantics tree over D-Bus: Accessible (roles, states, attributes, relations), Component (screen extents, hit-testing), Action (click/toggle), Value (slider read **and** write), Application, and **Cache** — the last is how libatspi bulk-loads a tree, and without it a client sees the app and nothing inside it. ARIA→AtspiRole maps in the same table shape as the UIA bridge, so a control that reads correctly to Narrator reads correctly to Orca. Threading is identical to the Windows leg because the hazard is: D-Bus calls read an immutable snapshot published after each drawn frame; actions queue to the UI thread and run through the ordinary click machinery (`AccessibilityActivate`/`Focus`/`SetValue`, path-addressed so ids survive the per-keystroke rebuild). Change notification: `StateChanged` per flipped state bit, `PropertyChange` on rename, focus on **both** ends of a move, and `Cache.AddAccessible`/`RemoveAccessible` for structure — which matters more here than in most toolkits, since CupriFace rebuilds the tree per keystroke, making structural churn the common case rather than the rare one. **Portability: zero interop.** AT-SPI is D-Bus over a Unix socket, not an OS API, so unlike `UiaInterop.cs` this bridge contains no P/Invoke and no native library — Tmds.DBus.Protocol is ~240 KB of managed IL that publishes trim-clean, and a Windows app carries it without ever loading it. The gate (`tools/atspi-gate.{sh,py}`, pyatspi over libatspi — the channel Orca uses) stands up a private a11y bus and registry under xvfb and asserts: the tree is served with real roles and screen extents (46 accessibles on the showcase), DoAction genuinely flips a checkbox, that flip arrives back as `object:state-changed:checked`, Value.Set moves a slider, and the tree still answers after an activation rebuilds it. `CUPRIFACE_ATSPI=0` is the kill switch, `CUPRIFACE_ATSPI_DEBUG=1` traces the conversation. Remaining inside this item: Text interface for editable fields, Selection on containers, and honouring the registry's event-listener registration (we currently emit unconditionally rather than only when something is listening). Same caveat as Windows: the GPU-less runner takes the SDL software path, which is what an RDP/VM user gets — the GL window carries identical wiring, but no CI machine proves that combination. |
| **NSAccessibility** bridge (macOS) | 🟢 | **Done (2026-08), proven by a blocking CI gate.** macOS asks the window's content VIEW for accessibility, and that view belongs to SDL — so the bridge builds a subclass of whatever class the view actually is **at runtime** and re-points that one instance at it (`object_setClass`, the mechanism KVO uses): our methods answer, everything else falls through to SDL, and no other view in the process is touched. Each node gets a small Objective-C object created the same way, holding only its node id in indexed ivars; ids are per structural path and never reused, so an element VoiceOver holds keeps meaning the same control across the per-keystroke rebuild. Serves role + subrole (a `switch` is an `AXCheckBox` with the `AXSwitch` subrole; a `tab` is an `AXRadioButton` in an `AXTabGroup` — genuinely how Cocoa models both), label, value with min/max, parent/children, frame, enabled/focused, `AXPress`, and `setAccessibilityValue:`; focus moves post `NSAccessibilityFocusedUIElementChangedNotification`. Actions queue to the UI thread and run through the ordinary click machinery, exactly as the other two do. **Interop is one quarantined file** (`ObjC.cs`) — a CI probe established first that runtime class creation with `[UnmanagedCallersOnly]` implementations works through libobjc with **no compiled Objective-C shim**, which is what kept macOS from becoming the first platform to force a hand-written native library into the project. The gate (`tools/nsa-gate.{sh,py}`, pyobjc over the AX client API — the channel VoiceOver uses) asserts what the bare window cannot produce: 155 AX elements including the app's own named controls, `AXPress` genuinely flipping a checkbox, `AXValue` moving a slider, and the root filling the window's content area **in points**. That last one is not decoration: it caught the engine's logical units reaching AppKit unscaled (a 30-unit button claiming 30 points instead of 26.9, an error that grows with distance from the origin). `CUPRIFACE_NSA=0` is the kill switch, `CUPRIFACE_NSA_DEBUG=1` traces attach and geometry. Remaining inside this item: `accessibilityHitTest:` (VoiceOver's mouse-follow), text ranges for editable fields, and value/structure notifications beyond focus. |
| **Web hidden-DOM a11y** | 🟢 | **Done** — `CupriDocument.BuildAriaHtml` serialises the semantics tree to an ARIA fragment (`role` + `aria-label`/`aria-checked`/`aria-valuenow-min-max`/`aria-disabled`/`tabindex`); the WASM host mirrors it into an off-screen, screen-reader-visible `<div>` (clip pattern, `aria-live`) beside the `aria-hidden` canvas, updated on input-driven repaints. Verified headlessly (roles/labels/states + updates on model change). |
| End-to-end screen-reader verification of the control gallery | 🟡 | All four platforms are automated-client verified (FlaUI over the Narrator channel, pyatspi over Orca's, pyobjc over VoiceOver's, uiautomator over TalkBack's), which proves the tree, the roles, the states and that actions change the app. What no automated client can judge is what a human hears: announcement wording, reading order, live regions. That pass — real Narrator/NVDA, real Orca, real VoiceOver, real TalkBack — hasn't been done on any of them. |
| Off-screen nodes are announced as visible | 🟢 | **Done (2026-08), gated on all three platforms.** The shared semantics tree now follows the clip chain — the viewport, then every `overflow` ancestor, using the SAME condition the painter uses to emit a `PushClip`, so what paints clipped and what reads as off screen cannot disagree — and marks each node `Offscreen`. Any overlap counts as visible: a control half scrolled into view is one the user can see and reach. Each bridge then surfaces it the way its platform expects: UIA's `IsOffscreen` property, AT-SPI's SHOWING dropped while VISIBLE stays (the exact distinction that pair of states exists for), and on macOS element hiding — an off-screen node stops being an accessibility element and the system splices it out. Four engine tests cover the geometry (below the viewport, clipped by a scroller, straddling the edge, plainly visible); each gate proves the end of it against a real AT client, the macOS one by asserting that the 88 reachable-but-off-screen controls it used to count are now zero. |

## 2. CSS engine (P2)

Ambition is the modern core; these are the sequenced-but-unshipped pieces (DESIGN §8, §12 caveats).

| Item | Status | Notes |
|------|--------|-------|
| **CSS transitions** | 🟢 | **Done** — `transition: <prop> <dur> [easing] [delay]` (comma-separated) animates `opacity`, `background`/`color`/`border-color`, `transform` and **`filter`** when their target value changes (hover, class/model change, theme toggle). Easing keywords (`linear`/`ease`/`ease-in`/`ease-out`/`ease-in-out`) **and `cubic-bezier(x1,y1,x2,y2)` literals** (incl. overshoot), via a Newton cubic-bézier solver; parsing is paren-aware so a `cubic-bezier()`'s inner commas don't break the list. `filter` chains interpolate op-by-op (a missing side pads to identity filters; mismatched chains fall back to discrete). State keyed by structural path so it survives the per-interaction rebuild. Paint-only (no relayout), driven by the same per-frame `Animate` clock as `@keyframes`. Follow-ups: width/height (layout-affecting) transitions, per-property longhands. |
| **Hover flicker, reported from a real project** | 🟡 | **One cause fixed, the rest unreproduced (2026-08-20).** Second-hand report: an agent building on CupriFace saw "lots of flickering or blinking" when moving the mouse over an element. **Fixed the same day** (`0059985`): a model refresh replaces every DOM element, which dropped `:hover` until the pointer moved again — so on a periodically-refreshed page every tiny movement re-applied hover and restarted its transition under a nearly-still cursor. The document now re-hit-tests the last pointer position against the fresh tree. **The engine side is now measured rather than assumed (2026-08-21)**, by six headless probes (`HoverStabilityTests`) that hold the boundary a host repaints from — a dispatch returning true. All six pass, so none of these is the cause: moving inside one element is silent after the first move; so is moving across a region with no element under the pointer; a crossing reports exactly one change; a `:hover` rule that RESIZES its own element does NOT oscillate under a still pointer (the classic CSS flicker — the engine does not feed layout back into hit-testing); hover survives a model rebuild; and repeated refreshes under a motionless cursor do not restart the hover transition (the fix above, now pinned). Also checked and cleared: `:hover` in a stylesheet works normally — `CssParser` rewrites it to `[data-hover]` — so an app is not forced to hand-roll hover and rebuild per mouse move. **Still unreproduced**, and now narrowed to app-shaped or host-shaped causes: what remains is the report's own missing evidence — the version, and the markup/CSS of the element that blinked. |
| Real **`:hover` / `:active`** pseudo-classes | 🟢 | **Done** — authored as `:hover`/`:active`/`:focus` (rewritten to marker attributes the engine toggles). `:hover` follows the pointer; `:active` marks the pressed element chain on pointer-down and clears on pointer-up (holds while held, like a real button press). |
| **`filter`** | 🟢 | **Done** — `filter: blur() brightness() contrast() grayscale() saturate() sepia() invert() opacity() drop-shadow()`, composed into one `SKImageFilter` (colour-matrix ops fold into a colour filter; blur/drop-shadow are image filters) and applied via a `SaveLayer` wrapping the element's subtree. Animatable via `transition` (op-by-op). |
| **Border style keywords** (`solid`/`dashed`/`dotted`) | 🟢 | **Done** — `border-style` (and the keyword in the `border` shorthand) parsed to `BorderLineStyle`; the rasteriser dashes/dots the uniform border stroke via a dash path effect (`none`/`hidden` suppress it). |
| Grid: **named lines** + **multi-row spans** (`rowSpan>1`) | 🟢 | **Done** — `grid-template-columns/rows` parse `[name]` line names into a name→line map; `grid-column`/`grid-row` accept named lines (`main-start / main-end`) resolved at layout time, and `grid-row: span N` spans multiple rows (row heights summed + inter-row gaps). |
| **Inline formatting context** (rich inline flow) | 🟢 | **Done** — a block with ≥2 consecutive inline-level children runs a real IFC: text and inline / inline-block elements flow into wrapping line boxes (word wrap, per-run fonts/weights/colours, mixed sizes centred per line, shrink-to-fit inline-blocks). Inter-run whitespace is preserved via `WsBefore`/`WsAfter` (no whitespace-only DOM nodes, so flex/grid are untouched); a lone inline child keeps the original per-node path (fields/textareas unchanged). Follow-ups: painted background/border/padding on a wrapping inline element (currently only its text flows), true baseline alignment, and `text-align:justify`. |
| Full **bidi line-breaking** (UBA) | 🟡 | Simplified bidi reorder ships; the full Unicode Bidi Algorithm remains. |

## 4. Performance & threading (P1)

Sustained fluidity is the core requirement (DESIGN risk #0); a demo hitting 60 fps isn't enough.

| Item | Status | Notes |
|------|--------|-------|
| Render-thread split in the **interactive windows** | 🟢 | **Done for the CPU/SDL path.** `CupriDocument.BuildFrame` is the UI-thread half (layout + paint → immutable `DisplayList`, no rasterise); a new `ThreadedPresenter` (over `ThreadedRenderer`) rasterises off-thread and hands back the latest frame via one lock-guarded buffer. `DesktopHost` uses it for the SDL software window when `CupriApp.ThreadedRender` is set. Verified headlessly: threaded raster matches single-threaded pixels, `Commit` never blocks + coalesces latest-wins, and `ThreadedPresenter.Present` draws the correct frame. Remaining: the GL path renders inline (threading it needs a background GL context — the per-backend piece). |
| **List/tree virtualization** | 🟢 | **Done (paint-culling).** A scroll container skips painting children whose box is entirely outside the visible band (+margin), so a long list costs paint+raster for the on-screen rows only — the win during scroll. Layout is untouched (culling is paint-only); transparent, no API/markup change. Follow-up: also skip layout for off-screen rows (needs app-cooperative windowing). |
| **CI perf-budget gates** | 🟢 | **Done** — `PerfBudgetTests` runs in the existing CI job (`dotnet test -c Release`), so a regression fails the build. CI hardware is shared and variable, so the gates are **ratios measured inside one process** (a document against a variant of itself, sampled interleaved and taken as medians) rather than absolute milliseconds — machine speed cancels, and each ratio encodes an invariant: styling doesn't scale with stylesheet size, hovering doesn't either, rebuilding doesn't scale with hidden content, a hover costs less than a rebuild, an unchanged frame presents nothing, and a move inside one element is a no-op. Each was verified to FAIL when its optimisation is reverted (×3.95, ×5.17, ×2.17). One deliberately loose wall-clock backstop (400 ms) catches only the catastrophic; a tight absolute number on a noisy runner is a flaky gate, and a flaky gate gets disabled. |
| **Live-resize fluidity** during the OS modal resize loop | 🟢 | Reflow itself is instant, and BOTH backends now have the streaming machinery: Windows and macOS run a modal loop while a window edge is dragged, so the render loop gets no turn until the mouse is released and a frame left to "next tick" arrives when the drag *ends*. The GL window therefore repaints from GLFW's framebuffer-resize callback (`DoRender` inside `OnFramebufferResize`), and the SDL window from an `SDL_AddEventWatch` callback, which SDL dispatches synchronously from inside that modal loop. **What was missing was not the code but any way to know it works** — the GL path swallowed re-entrancy failures in a bare `catch {}`, so it could do nothing and look identical. Both paths now count the frames they paint (`ResizeFrames`), `CUPRIFACE_RESIZE_DEBUG=1` traces each one, and a refused repaint prints once instead of vanishing. **Confirmed (2026-08) by a human drag on Windows, GL window**: frames stream during the drag rather than arriving on release. That last step resists automation and always will — an external `SetWindowPos` is not the modal loop, and nothing can hold a mouse button down inside one — so this row rests on a person's eyes plus the trace, not on a gate. Not yet drag-confirmed: the SDL software window and macOS. Both carry the same counters and the same `CUPRIFACE_RESIZE_DEBUG=1` trace, so each is a one-drag check whenever someone is in front of one. |

| **macOS window path segfaulted on GL-less virtual Macs** | 🟢 | **Fixed (2026-08), proven in CI.** The macOS crash report named it: `glfwCreateWindow` fails on a Mac with no OpenGL (the paravirtual GPU of virtualised Macs — CI runners are `VirtualMac2,1`) *without setting a GLFW error*; Silk.NET then applies its default window position to the NULL handle, and release-build GLFW (asserts compiled out) dies with SIGSEGV inside `glfwSetWindowPos` — before any managed guard can run, so uncatchable in-process. Fix: on macOS the host first spawns itself as a disposable probe child (`--cupriface-gl-probe`) that attempts full GL bring-up and reports by exit code; if the child dies, only the child dies, and the real process goes straight to the SDL software window. Real Macs (GL present) pay one invisible ~200 ms probe and keep the GPU window. The macOS CI smoke runs BOTH paths every push. |
| **Linux window path segfaults on a GPU-less/virtual X server** | 🟢 | **Fixed (2026-08), proven by a blocking CI gate.** Root cause, caught by the `CUPRIFACE_GL_DEBUG` loader trace running on the failing machine itself: Skia probes for **EGL** entry points (`eglQueryString`, `eglGetCurrentDisplay`) through whatever loader it is given, and ours forwarded every name to GLFW — on X11 that is `glXGetProcAddressARB`, which is *specified* to fabricate a dispatch stub for any name it does not recognise. It returned confident non-null garbage for the egl* probes, Skia concluded EGL existed, called the stub, SIGSEGV. Null would have been handled (Skia null-checks and skips EGL detection) — the lie killed, not the lack. Fix: the loader answers only for `gl*` names (`SkiaWindow`). The CI Linux job now runs the GL path under xvfb+llvmpipe — the exact configuration that used to die — as a **blocking** smoke test with the trace left on, so any regression names its killer. `CUPRIFACE_SOFTWARE=1` remains as a deliberate escape hatch. Two failed attempts are recorded in git history (a `glGetString` null-guard; assuming the probe call itself was the problem) so they are not retried. |

| **Two-axis scrolling** | 🟢 | **Done (2026-08).** A box whose content is too wide scrolls sideways, with its own momentum. The gesture is two fingers the page owns: a lone finger is never consumed (taps, scrolling and flings are untouched) and **capture wins**, so a collage tile or a map that opted into `OnManipulate` keeps both fingers. `PageZoomEnabled` opts out, as a browser's viewport meta does. Hosts forward uncaptured pointers and cancel their single-pointer gesture when a pinch engages, or the page would scroll under the fingers. Twelve tests, including the two that matter: one finger is not a pinch, and an element that owns the gesture keeps it. **Keyboard and wheel reach it too (2026-08-21)**: Ctrl/Cmd `=`/`−`/`0` and Ctrl+wheel walk a discrete browser ladder (0.5…4, so repeated in/out returns *exactly* home; from a pinch's in-between value the next press lands on a rung, in the pressed direction). The split honours the portability law — the engine owns the ladder (`ZoomIn`/`ZoomOut`/`ZoomReset`), the hosts own the chords (both desktop windows forward `=`/`−`/`0` and keypad equivalents through the same Shortcut seam the clipboard uses; the wheel event grew a mods parameter) — and it honours `PageZoomEnabled`, **except `Ctrl+0`, which always works**: an escape hatch nothing can close. Proven layered, stated plainly: the ladder by four engine tests; **Ctrl+wheel by the UIA gate on CI, end to end, on every push** — a real client holds Ctrl, rolls the wheel over the SDL window, and watches a checkbox's UIA rect grow one rung (×1.1) and roll back down: the same scaled-bounds claim the pinch makes, asserted through the wire Narrator uses. The chord path (Ctrl+`=`/`−`/`0`) runs in the same gate wherever a session can type at all — which the hosted runner cannot: eleven instrumented runs established that its input stack delivers mouse input and modifier state but **eats ordinary payload keys** (Tab, `=`, `0` never arrived under either SendInput dialect, while exotic F13 slipped through), so the gate probes with a literal Tab against the window's own testimony (`CUPRIFACE_KEY_DEBUG` — both windows log every key/focus event they receive, printed when the gate ends) and runs the chord legs strict where the probe lands, as on a normal desktop (recorded local pass: focus moved, width 31→33→31), skipping them with the reason printed where it cannot. The hunt also replaced the gate's vacuous Tab check ("anything has focus" — guaranteed by an earlier pattern action) with one that requires focus to MOVE. **Restoring a remembered level is supported; storing it is the app's (2026-08-22).** `Zoom` is settable before the first frame — assign it in the host's configure hook (`DesktopHost.Run(app, doc => doc.Zoom = Prefs.Zoom)`, `ConfigureDocument` on Android) and the first frame a user sees is already at their level rather than jumping from 1 — and `ZoomChanged` reports every settled level so an app knows when to save, including the pinch/chord/wheel changes it could not otherwise observe. The event carries the clamped value (what you store round-trips) and stays silent when a change lands on the current level, so a held key cannot hammer a handler that writes to disk. **The engine stores nothing**: a UI toolkit that picks a settings location for you is one you fight later. Four tests cover the startup frame, all three input routes, the clamped round-trip, and the held-key case. **Ctrl+wheel now zooms at the pointer (2026-08-22)**, via `ZoomIn(hostX, hostY)` / `ZoomOut(hostX, hostY)` — the parameterless pair still zooms from the origin, which is what a keyboard chord wants. The anchor is an ELEMENT re-found by structural path, not a coordinate, and reflow forces that: at a new level the text rewraps, so "the point that was at y=400" is not a promise this engine can keep, while "the paragraph you were pointing at" is — the same path-keying that carries flings and focus across a rebuild. After the reflow the scroller under the cursor is corrected by the difference between where the anchor is drawn and where it was, in host pixels. Five tests, including the one that keeps the others honest: the UNanchored call from the same state does move the row, so the anchored assertion is measuring something. |

**A note on proof.** The IME contract and autofill are the features here that CI structurally
cannot drive: it cannot type on a real keyboard or install a fill service. Their engine halves are
covered by headless tests; the platform halves rest on a documented manual pass. That is stated
rather than papered over — and it is why the phone sample carries a surface for each of them (a
gesture tile, a sideways row, autofilled fields), so the manual pass has something to press.

**Multi-touch used to be on that list and no longer is.** `adb shell input` is single-pointer, which
is why the seam shipped without a gate — and a device then found a two-finger bug CI could not have
caught. The gate now speaks the multi-touch protocol itself and elects its transport empirically
(the emulator console; `sendevent` is permission-denied to the shell user, and the emulator exposes
eleven virtio touch devices of which one drives the display). It proves each link separately: a
trusted single tap, a canary that finds the live device, both fingers landing together, a second
finger arriving late, and the same pinch repeated. Five CI rounds to build, and the lesson worth
keeping is that every one of those rounds failed for a reason inside the harness rather than inside
the product.

### Parked: verifying autofill

Implemented, plausible, unproven — and it needs a human with a password manager, so it is written
down rather than left in someone's memory. On a device with a manager installed (Vaultwarden,
Bitwarden, 1Password…), running the phone sample's **Form** page:

1. Tap **Email**. Expect the manager's inline chip in the keyboard strip, or a fill dropdown. This
   is the load-bearing signal: it means a fill SESSION exists. Everything else depends on it.
2. Fill both fields (by hand is fine) and press **Sign in**. Expect an offer to SAVE.
3. If neither appears, `adb logcat -s cupri:I` while tapping the field shows the host's focus and
   pointer markers — whether the announcement fires at all is the first fork in the diagnosis.

Known unknowns if it still fails: whether the manager uses the Autofill framework at all (some use
an accessibility service instead, which is a different integration), and whether `SubmitForm()`
reaches `Commit()` before the field values have been reported to the session.

## Non-goals (won't do — by design)

Per [DESIGN.md §1](DESIGN.md); listed here so "deferred" is never confused with "planned but missing":

- **A JS engine in the runtime**, or JavaScript in app UI pages. (The web target's non-authored
  bootstrap/interop glue is expected and separate.)
- **100% CSS spec compliance** — we chase the modern core and consciously skip legacy cruft:
  `float`-based layout, multi-column, print/`@page`, obscure pseudo-classes.
- **A full DOM `document.*` scripting API** — there's no script to call it.
